Part 1: B+ Tree Implementation (77 points)

For this part of the project, you are expected to implement basic functionality to a B+ tree using the algorithms discussed in class. The required operations are:

  • Btree::insert()
  • Btree::remove()
  • Btree::search_range(), returning every item in the inclusive range

Duplicates should not be stored in this B+ tree. We have provided skeleton code as well as implementations of some basic functions so that you do not have to start from scratch. It is advised that you familiarize yourself with B+ tree operations thoroughly before starting.

Download the P4 starter files before beginning Part 1.

We have provided you with an implementation of Btree::search() as a simple example of how you can interface with the skeleton code. We have also provided basic operations for the B+ tree node classes. The starter archive identifies which functions are given and which functions you must implement.

What you need to do

  1. Implement Btree::insert() as described in lecture. Prefer splitting nodes over redistribution.
  2. Implement Btree::remove() as described in lecture. Prefer redistribution over merging.
  3. Implement Btree::search_range(). Include all Data* values between the given range, inclusive.

Specific rules for splitting, redistribution, and merging

Follow these general rules when implementing the above functions:

  1. When splitting:
    • Push the smallest value of the newly split right node up to the parent.
    • For leaf nodes, first split existing nodes evenly between the left and right node. Then insert the new value into the appropriate, valid node based on the existing values and the insert value. There are cases where both nodes are valid. In these cases, add the value to the left node.
  2. When redistributing:
    • For leaf nodes, update the appropriate parent node with the smallest value in the right node. Redistribute with any valid left or right nodes.
    • For inner nodes, only redistribute with sibling nodes.
    • Prefer redistribution with the right node over the left node.
    • The right-hand side will always have more values than the left-hand side, if not equal. The right-hand side and left-hand side should have the same number of values. When this is impossible due to an odd number of values, the right-hand side should have one more value than the left-hand side.
  3. When merging:
    • For leaf nodes, merge with any valid left or right nodes.
    • For inner nodes, only merge with a sibling node.
    • Prefer merging with the right node over the left node.
    • Always merge the right node values into the left node.

Remember to maintain the private variable size while implementing the above functions. The capacity of each inner node must always be between (BTREE_FANOUT - 1) / 2 and BTREE_FANOUT - 1, except when it is the root node. The capacity of leaf nodes must be between BTREE_LEAF_SIZE / 2 and BTREE_LEAF_SIZE, except when the leaf is the root node.

BTREE_FANOUT is guaranteed to be odd and BTREE_LEAF_SIZE is guaranteed to be even. Always use the constants defined in constants.h, such as BTREE_LEAF_SIZE and BTREE_FANOUT. The B+ tree should initially start empty, with its root node being a Bnode_leaf*. When this leaf node has to split, change the root node to a Bnode_inner. The root should turn back into a Bnode_leaf when its size is less than BTREE_LEAF_SIZE.

Exercise 8: Inside a PostgreSQL B+ tree

A PostgreSQL index created with CREATE INDEX is a B+ tree, just like the one you implement in Part 1. Each node is one 8 KB disk page. Inner pages hold separator keys and child pointers; leaf pages hold (key, record id) entries and are linked to their neighbors. This is Alternative 2, the same layout as the Data entries in constants.h. The pageinspect extension lets you look at these pages directly. It ships with standard PostgreSQL installations and requires a superuser, which you are by default on a local installation.

Start from a freshly loaded database and run:

SET enable_bitmapscan = off;
CREATE EXTENSION IF NOT EXISTS pageinspect;
-- deduplicate_items = off stores one (key, record id) entry per row, like
-- Part 1. By default, PostgreSQL 13+ merges duplicate keys into one entry.
CREATE INDEX ix_orders_custid ON orders (customerid) WITH (deduplicate_items = off);
ANALYZE orders;

-- Root page number and height of the tree. PostgreSQL numbers levels from
-- the leaves upward: leaves are level 0, so level = number of inner levels.
SELECT root, level FROM bt_metap('ix_orders_custid');

-- Total number of pages in the index (page 0 is a metadata page, not a node).
SELECT pg_relation_size('ix_orders_custid') / 8192 AS index_pages;

-- Statistics for one node. Replace ROOT with the root page number from above.
-- type: r = root, i = inner, l = leaf. btpo_prev / btpo_next are sibling links.
SELECT type, live_items, btpo_prev, btpo_next, btpo_level
FROM bt_page_stats('ix_orders_custid', ROOT);

Answer the following:

  1. Report the height of ix_orders_custid, the number of children of the root, the total number of leaf pages, and the number of entries in the leftmost leaf. To find the leftmost leaf, use the page that the root's first entry points to; you can list the root's entries with bt_page_items('ix_orders_custid', ROOT), where the first number of the ctid column is the child page (ignore the second number in inner pages).
  2. Starting from the leftmost leaf, follow btpo_next through three leaves and report each page number and its live_items. Which operation in Part 1 depends on leaves being linked like this, and why?
  3. The orders table has 12,000 rows. Using the Part 1 constants in the starter constants.h (BTREE_FANOUT = 5, BTREE_LEAF_SIZE = 4), compute the smallest and largest possible height of a Part 1 B+ tree holding 12,000 keys, using the node capacity rules in Part 1. Compare with the height you measured in (a). In one or two sentences, explain what makes PostgreSQL's fanout so much larger.
  4. Now build an index on a much wider key: 
    CREATE INDEX ix_customers_wide ON customers (address1, email, lastname, firstname, city);
    Report the height and number of pages of ix_customers_wide and of the primary key index customers_pkey (both index the same 20,000 rows). Explain the difference in terms of fanout. Drop ix_customers_wide when you are done.

Exercise 9: Predicting when the plan changes

An index range scan follows the same steps as Btree::search_range(): descend from the root to the first matching leaf, walk the leaf chain until the range ends, and then, because the index uses Alternative 2, fetch each matching record from the table (the heap). Whether those heap fetches are cheap depends on whether the table is stored in roughly the same order as the index, i.e. whether the index is clustered. In this exercise you will use that cost model to explain when the optimizer switches between an index scan and a sequential scan.

Keep ix_orders_custid from Exercise 8 and add a second index:

SET enable_bitmapscan = off;
CREATE INDEX ix_orders_date ON orders (orderdate);
ANALYZE orders;

-- correlation close to 1 or -1: table order matches index order (clustered)
-- correlation close to 0: table order is unrelated to index order (unclustered)
SELECT attname, correlation FROM pg_stats
WHERE tablename = 'orders' AND attname IN ('customerid', 'orderdate');
  1. Report the correlation of customerid and orderdate. Which of the two indexes behaves like a clustered index?
  2. Run EXPLAIN SELECT * FROM orders WHERE customerid <= k; for k = 50, 100, 200, 500, and 2000, and EXPLAIN SELECT * FROM orders WHERE orderdate <= d; for d = '2009-01-15', '2009-04-01', '2009-07-01', '2009-10-01', and '2009-12-15'. For each query, record the scan type and the estimated number of rows. For each column, report the approximate fraction of the table (estimated rows ÷ 12,000) at which the optimizer switches from an index scan to a sequential scan.
  3. Force index scans with SET enable_seqscan = off; and run: 
    EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE customerid BETWEEN 1 AND 100;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE orderdate BETWEEN '2009-01-01' AND '2009-01-03';

-- number of distinct table pages that hold the matching rows
SELECT count(*) AS matching_rows,
       count(DISTINCT (ctid::text::point)[0]) AS heap_pages
FROM orders WHERE customerid BETWEEN 1 AND 100;
    Report the actual rows and the Buffers: shared hit/read total for each query, and run the heap_pages query for both ranges. Using your tree height from Exercise 8, break each buffer count into (1) pages read while descending the tree, (2) leaf pages scanned, and (3) heap page accesses. A heap page is counted again each time the scan leaves it and later comes back to it, so heap accesses can exceed heap_pages. Use this breakdown to explain your switch points from (b). Run RESET enable_seqscan; afterward.
  4. Physically reorder the table by customer and repeat the correlation query and the queries from (b): 
    CLUSTER orders USING ix_orders_custid;
ANALYZE orders;
    Extend the ranges from (b) as needed to find the new switch points: also try k = 4000, 8000, and 12000, and d = '2009-01-03'. How did the correlations and the switch points change for each column? Explain why using your answer to (c). Is "clustered" a property of the index, or of how the table is stored? CLUSTER changes the table permanently, so reload the database before rerunning any other exercise.

The exact switch points and buffer counts depend on your PostgreSQL version and settings, so they may not match your classmates' numbers. You will be graded on whether your measurements are consistent with each other and on the reasoning in your explanations, not on matching specific numbers.
